**Task:** você é um gerador de agentes de IA e abaixo está uma especificação de um agente. Gere um agente conforme a especificação. Considere que as ferramentas do agente devem ser geradas junto ao código do agente.  
**Contexto:** Um agente de IA é uma entidade que usa LLM e ferramentas para executar tarefas específicas de forma autônoma.   
**Output:** `agent.py`, `requirements.txt`, `tests.py`  
**Contrato de interface com o benchmark:**

| Requisito de interface | Exigência fixa |
| :---- | :---- |
| Modelo | GPT-4o |
| Framework | LangGraph |
| GenAI Tool | ChatOpenAI |
| Entrypoint | agent(...) |
| Output | state: dict contendo o perfil do usuário (user_data), o plano vigente (fitness_plan), o feedback (feedback), o histórico de progresso (progress) e as mensagens trocadas (messages) |

**Requisitos:**

| Requisito | Significado | Especificação do Agente | Critério de Corretude |
| :---- | :---- | :---- | :---- |
| Goal | Objetivo e comportamento principal do agente na voz ativa | O Agente AI Fitness Coach cria um perfil do usuário a partir dos dados informados, gera um plano de treino semanal personalizado, ajusta o plano conforme o feedback recebido, registra o progresso e envia mensagens motivacionais, devolvendo ao chamador o perfil, o plano vigente, o histórico de progresso e todas as mensagens trocadas durante a execução. | O comportamento principal está declarado definindo quem faz, o que faz e o resultado? |
| Persona (Opcional) | A personalidade que o agente assume ao realizar as tarefas | Personal trainer digital com tom encorajador, direto e sem jargão técnico não explicado, voltado ao treinamento físico e a hábitos de bem-estar de praticantes amadores. Todos os textos produzidos pelo agente seguem essa voz. | A especificação define uma persona e sua área de atuação? A persona é adequada/coerente com o Goal? |
| Inputs | Informação enviada para o agente | No modo criação, o agente recebe os dados do usuário: idade, peso, altura, gênero, objetivo principal, prazo do objetivo, preferências de treino (modalidades preferidas, dias da semana disponíveis e duração desejada por sessão), nível de atividade física, condições de saúde, limitações físicas, restrições alimentares e, opcionalmente, preferências adicionais. No modo atualização, recebe o estado devolvido por uma chamada anterior e um feedback em linguagem natural sobre o plano vigente. | A especificação define qual é a entrada esperada? |
| Tools | Lista com as ferramentas disponíveis e para que elas servem | O agente não utiliza ferramentas além da GenAI Tool fixada no contrato de interface (ChatOpenAI). Por meio dela, executa todas as etapas de linguagem natural — estruturar o perfil, gerar o plano, classificar o feedback, ajustar o plano, pedir esclarecimento, resumir o progresso e escrever a mensagem motivacional —; em cada etapa, a entrada é o prompt com os dados necessários à etapa e o retorno é o texto produzido pelo modelo. O agente não navega na internet e não acessa arquivos nem bancos de dados. | A especificação define a ferramenta, seus parâmetros, o retorno e o propósito de uso dela estão definidos? |
| Constraints | Uma afirmação que restringe as ações que o agente (ou seus usuários/operadores) têm permissão de realizar. Descreve o que o agente deve, não deve, ou não pode fazer, ou define que apenas determinados papéis/condições autorizam uma certa ação. | - Segurança médica. O agente não emite diagnóstico médico nem prescreve tratamento ou medicação; quando o usuário informa condições de saúde, o plano deve incluir a recomendação de consultar um profissional de saúde antes de iniciar. - Recusa de entrada inválida. O agente não gera plano a partir de dados ausentes, incompletos ou inválidos; informa cada problema encontrado e o que era esperado. - Limites do plano. Nenhuma sessão excede a duração que o usuário escolheu e nenhum treino é agendado fora dos dias informados. - Histórico imutável. Mensagens e entradas de progresso já registradas não são alteradas nem removidas; o agente só acrescenta ao final. - Não persistência. O agente não grava dados pessoais em arquivos, bancos de dados ou armazenamento externo; dados pessoais aparecem apenas nos prompts enviados ao LLM, e os registros de log não os contêm. | A especificação declara explicitamente uma ação que o agente deve, não deve, ou só pode sob certas condições? A restrição está expressa em termos de ação/comportamento permitido ou proibido — não em termos de tecnologia, ferramenta ou biblioteca usada para implementar o agente? Quando a restrição envolve papel/autorização ("só X pode fazer Y"), a especificação define quem ou o que está autorizado? A restrição é verificável: é possível observar, no comportamento do agente, se ela foi violada ou respeitada? |
| Policies/Invariants | Afirmações que descrevem o que é verdadeiro sobre o domínio ou sobre o estado do agente em um dado momento, e que devem permanecer válidas durante toda a execução. Descrevem relações, propriedades ou condições do mundo/domínio que servem de base para o comportamento do agente. | - O estado devolvido contém sempre o perfil, o plano vigente, o feedback, o histórico de progresso e as mensagens trocadas, e cada mensagem identifica quem falou (usuário ou agente). - Todo plano devolvido cobre as mesmas cinco partes: tipos de exercícios, duração e frequência, níveis de intensidade, dias de descanso e recomendações alimentares. - Todo plano devolvido respeita os dias e a duração escolhidos pelo usuário e está livre de diagnóstico e prescrição. - O perfil do usuário corresponde aos dados informados; o agente não inventa nem altera dados do perfil. - O histórico de progresso começa vazio e só cresce por acréscimo, preservando as entradas anteriores. | A especificação declara uma relação, propriedade ou condição do domínio que é (ou deve ser) sempre verdadeira, e não uma ação permitida/proibida? O invariante está conectado a uma entrada, saída, evento ou dado que o agente efetivamente manipula (não é conhecimento de domínio irrelevante ao escopo do agente)? É possível verificar, a qualquer momento durante a execução, se o invariante ainda é válido? |
| Quality attributes (non-functional requirements) | Características observáveis do comportamento do agente durante a execução, que não descrevem o que ele faz (isso é Goal/Behavior Requirements) nem o que ele nunca deve fazer (Constraints), mas quão bem ele faz — de forma consistente, segura, eficiente e confiável. Moldam diretamente a confiança e a experiência de quem depende do agente. | - Robustez. Diante de falha momentânea da ferramenta de LLM, o agente tenta novamente e, esgotadas as tentativas, encerra com uma mensagem de falha ao usuário, sem interromper a execução com erro. - Consistência. Em execuções repetidas com a mesma entrada válida, todo plano devolvido respeita os dias e a duração escolhidos e as cinco partes do plano. - Latência. A criação de um plano termina em até 2 minutos e a atualização por feedback em até 3 minutos, medidos do início ao fim da chamada agent(...) e sem considerar o tempo gasto em novas tentativas. - Rastreabilidade. A execução produz registros de log que permitem reconstruir a ordem das etapas executadas, sem conter dados pessoais. Em trade-off, robustez tem prioridade sobre latência. | O atributo está descrito de forma observável/mensurável no comportamento (não é uma característica de implementação, ex: "usar cache" não é quality attribute, é constraint de implementação)? Existe um critério de aceitação verificável (limiar, taxa, ou condição de teste), e não apenas um adjetivo vago ("deve ser rápido" sem definir o quê é rápido)? Havendo trade-off entre atributos (ex: robustez vs. performance), a especificação deixa explícita a prioridade? |

**Comportamentos**

| Comportamento | Trigger | Input | Tools | Expected Outcome | Environment Effect | Critério de aceitação |
| :---- | :---- | :---- | :---- | :---- | :---- | :---- |
| B1 — Criar perfil estruturado. O agente estrutura os dados do usuário em um perfil organizado, sem inventar dados, e apresenta o perfil em uma mensagem. | Chamada com os dados do usuário no modo criação. | Dados do usuário informados na criação. | ChatOpenAI (estruturação do perfil). | Perfil estruturado no estado e mensagem apresentando o perfil. | Acréscimo da mensagem de perfil às mensagens do estado; nenhum arquivo ou banco de dados é alterado. | Dados do usuário válidos, o perfil corresponde aos dados informados, sem campos inventados, e exatamente uma mensagem de perfil é acrescentada. |
| B2 — Gerar plano de treino personalizado. O agente gera, a partir do perfil, um plano de treino semanal com as cinco seções, respeitando as preferências, os dias e a duração escolhidos, sem diagnóstico nem prescrição e com o aviso de saúde quando o usuário informa condições de saúde. | Perfil criado. | Perfil do usuário. | ChatOpenAI (geração do plano). | Plano vigente gravado no estado e mensagem com o plano final. | Gravação do plano no estado e acréscimo da mensagem; nenhum arquivo ou banco de dados é alterado. | Dado perfil válido, o plano contém as cinco seções, respeita os dias e a duração escolhidos, não contém diagnóstico nem prescrição e inclui o aviso de saúde quando necessário; exatamente uma mensagem com o plano é acrescentada. |
| B3 — Ajustar plano conforme o feedback. O agente analisa o feedback sobre o plano vigente; quando ele indica claramente uma mudança, gera o plano atualizado mantendo objetivo, prazo, estrutura e limites; quando não indica, faz uma pergunta específica ao usuário em vez de alterar o plano. | Feedback do usuário com plano vigente. | Plano vigente e feedback. | ChatOpenAI (análise do feedback e ajuste ou esclarecimento). | Plano atualizado e mensagem correspondente, ou mensagem de esclarecimento sem alterar o plano. | Substituição do plano e acréscimo da mensagem, ou apenas acréscimo da pergunta; nenhum arquivo ou banco de dados é alterado. | Dado feedback claro, o plano atualizado responde ao feedback, mantém objetivo, prazo, as cinco seções e os limites, e uma mensagem é acrescentada; dado feedback vago, o plano permanece o mesmo e o agente pergunta o que deve ser esclarecido. |
| B4 — Monitorar progresso. O agente resume o percurso do usuário a partir do perfil, do plano e do histórico, com um encorajamento e uma sugestão de próximo passo, e registra o resumo no histórico. | Plano gerado ou ajustado. | Perfil, plano vigente e histórico de progresso. | ChatOpenAI (resumo do progresso). | Resumo acrescido ao histórico e mensagem correspondente. | Acréscimo de uma entrada ao histórico e da mensagem correspondente; nenhum arquivo ou banco de dados é alterado. | Dado estado válido, o histórico cresce em exatamente uma entrada não vazia, as entradas anteriores permanecem intactas e uma mensagem correspondente é acrescentada. |
| B5 — Enviar mensagem motivacional. O agente envia uma mensagem motivacional ou uma dica relacionada ao objetivo do usuário e encerra, devolvendo o estado final. | Após o registro do progresso. | Perfil, plano vigente e progresso mais recente. | ChatOpenAI (mensagem motivacional). | Mensagem motivacional acrescida e estado final devolvido. | Acréscimo da mensagem ao final das mensagens; nenhum arquivo ou banco de dados é alterado. | Dada execução concluída, o estado final contém exatamente uma nova mensagem motivacional e é devolvido ao chamador. |
| B6 — Recusar entrada inválida. Quando os dados obrigatórios estiverem ausentes, incompletos ou fora dos valores esperados, o agente não gera plano; envia uma mensagem listando cada problema encontrado e o valor esperado. | Dados obrigatórios ausentes, inválidos ou fora dos valores esperados, em qualquer modo. | Argumentos recebidos na chamada. | Nenhuma. | Mensagem de erro listando os problemas; nenhum plano é gerado e o estado é devolvido imediatamente. | Acréscimo da mensagem de erro; nenhum arquivo ou banco de dados é alterado. | Dados inválidos, nenhum plano é gerado, a mensagem lista cada problema com o valor esperado e a execução termina sem erro. |

| Campo              | Critério de corretude                                                                                                     |

A especificação cobre explicitamente o comportamento esperado diante de: entrada inválida, falha de ferramenta/tool call, ambiguidade, ausência de informação necessária? Os requisitos, somados, são suficientes para realizar o Goal declarado (nada essencial ficou implícito)? |
| Trigger            | A condição ou evento que inicia o comportamento está explicitamente definido e é observável?                              |
| Input              | A especificação define qual é a entrada esperada?                                             |
| Tools              | As ferramentas necessárias para o comportamento estão identificadas e seu propósito de uso está definido?                                             |
| Expected Outcome   | A especificação define qual alteração deve ocorrer no ambiente? A alteração esperada é observável e verificável após a execução do comportamento? |
| Environment Effect | A especificação define qual ambiente o agente vai alterar?  A especificação define como será feita a alteração no ambiente?                                 |
