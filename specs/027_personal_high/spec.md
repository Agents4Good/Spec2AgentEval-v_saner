**Task:** you are an AI agent generator and below is an agent specification. Generate an agent according to the specification. Treat the agent tools as generated together with the agent code.
**Context:** An AI agent is an entity that uses an LLM and tools to perform specific tasks autonomously.
**Output:** `agent.py`, `requirements.txt`, `tests.py`
**Benchmark interface contract:**

| Interface requirement | Fixed requirement |
| :---- | :---- |
| Model | GPT-4o |
| Framework | LangGraph |
| GenAI Tool | ChatOpenAI |
| Tools | Exactly two LangChain tools generated together with the code, with no network, no files, and no DB. Each tool must be a LangChain tool (`@tool`, `StructuredTool`, or obtained from an MCP server via `langchain-mcp-adapters`) and must run exclusively through its interface (`invoke`/`ainvoke`, directly or via `ToolNode`), never through a direct call to the function that implements it. In this specification the implementation uses local `@tool` or `StructuredTool`, because MCP with network conflicts with the network ban. `ChatOpenAI` is the model interface and does not count as a tool. The execution order is fixed and chained. |
| Entrypoint | agent(...) |
| Output | state: dict containing the user profile (user_data), the current plan (fitness_plan), the feedback (feedback), the progress history (progress), and the exchanged messages (messages) |

| Inputs | Information sent to the agent | In creation mode, the agent receives the user data: age, weight, height, gender, main goal, goal deadline, training preferences (preferred modalities, available weekdays, and desired duration per session), physical activity level, health conditions, physical limitations, dietary restrictions, equipamentos_disponiveis as a required list that may be empty to indicate equipment-free training and, optionally, additional preferences. Invalid inputs are rejected before any tool. | Does the specification define the expected input? |
| Tools | List of the available tools and what they are for | The agent uses exactly two LangChain tools generated together with the code, local and deterministic, with no network, no files, and no DB, run exclusively through `invoke`/`ainvoke` directly or via `ToolNode`. `ChatOpenAI` is only the model interface for feedback classification and language and plan steps and does not count as a third tool. Tool 1, `avaliar_parametros_treino`: receives `perfil` dict and optional `feedback` str or None. It preserves the stated data and returns `avaliacao` dict with a fixed snake_case schema: modalidades_preferidas list, dias_disponiveis list, duracao_maxima number, nivel_atividade text, intensidade_sugerida text, limitacoes_expressas list, equipamentos_disponiveis list, objetivo text, prazo text, and recomendacao_consulta bool always present with value true when health conditions exist. It queries a local in-memory catalog and returns a dict with `candidatos` list, `avaliacao_referencia`, `contexto_avaliacao`, `status`, and `motivo`. Each candidate contains nome, modalidade, equipamentos_necessarios list, intensidade_sugerida, and limitacoes_de_uso list. The selection accepts only exercises that use solely available equipment or that need no equipment, with filters for stated preferences and limitations. The return follows the closed status rule: `ok` requires a non-empty candidatos list and an empty motivo, `sem_opcoes` requires an empty candidatos list and a non-empty motivo. The second tool never receives perfil or feedback directly and never has the evaluation reconstructed by the model. Every exercise in the final plan must come from the candidates with status ok. | Does the specification define the tool, its parameters, its return, and its purpose? |

Tool 2 runs only after validated success of tool 1, with no parallelism, no inversion, no reuse of a prior evaluation, and no change to the evaluation by the model. In a failure-free path there is exactly one valid execution of each tool. Retries happen only on transient error, up to 3 total attempts with the same input and with the dependency preserved. Permanent error and invalid return produce no retry. - Restricted tool use. No LangChain tool runs with invalid input. Feedback classification uses ChatOpenAI before the tools. With vague feedback there are zero LangChain tools, with a clarifying question from the model. An update with clear feedback sends perfil and feedback to tool 1 and sends the exact new evaluation to tool 2. Invalid input, vague feedback, and missing candidates never produce an invented plan. - Provisional preparation with single commit. A new plan and progress summary stay provisional until the motivational message succeeds. The state commit happens only in B5. Failure at any step, including B1, B4, or B5, keeps the original plan and progress in update mode, or empty fitness_plan and empty progress in creation mode. The B9 error message is local and does not depend on the LLM. Already recorded messages are preserved. | Does the specification explicitly state an action the agent must, must not, or may only do under certain conditions? When the restriction involves role/authorization ("only X may do Y"), does the specification define who or what is authorized?
